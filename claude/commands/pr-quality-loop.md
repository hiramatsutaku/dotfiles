# PR 品質担保ループ

PR 作成後の品質担保を一括で行う。3 レビュアー（CodeRabbit + codex + 別プロセス Claude Code）を
**並列**で走らせ、指摘を統合して対応する周を最大 2 周 → 動作証跡 → 最終報告、の順で進める。

引数: PR 番号（省略時は現在のブランチに紐づく PR を `gh pr view` で特定する）。

## 全体フロー

```text
Phase 0: 前提確認
Phase 1: レビュー収集（3 レビュアーを並列で走らせ、結果を集めるだけ。ファイルは触らない）
         ├ ローカル codex           ─┐
         ├ ローカル headless claude  ├ 同時に起動
         └ CodeRabbit のポーリング  ─┘（REVIEW_SHA 基準・90 秒間隔・上限 10 分）
           └ レビューが来たら指摘本文まで取得（修正は Phase 2）
Phase 2: 指摘の統合 → 検証 → 修正 → push
         └ Phase 1 + Phase 2 を最大 2 周（新規の妥当な指摘が 0 なら 1 周で終了）
Phase 3: 動作証跡の添付（マージ前ゲート）
Phase 4: 最終報告
```

各フェーズの区切りで、PR 上のステータスコメントを更新する（次節）。

## ステータスコメント（随時更新）

ループはローカルで数十分かかるため、PR 側から進捗が見えない。
**PR に単一のステータスコメントを置き、フェーズが進むたびに書き換える**。新規コメントは増やさない。

### マーカーと検索

本文の 1 行目に必ず `<!-- pr-quality-loop-status -->` を入れる。
セッションをまたいでも、これで同じコメントを引き当てて更新し続ける（冪等）:

```sh
gh api "repos/{owner}/{repo}/issues/<pr>/comments?per_page=100" --paginate --slurp \
  | jq -r '[.[][] | select(.body | startswith("<!-- pr-quality-loop-status -->")) | .id] | first // empty'
```

該当が無ければ空文字が返る（exit 0）。空なら新規作成、id が取れたら更新に回す。

**`--paginate --jq` を使わないこと。** `--jq` はページごとに適用されるため、`| first` がページ単位で
効いてしまい、該当コメントが複数ページにまたがると id が複数行出力されて PATCH の URL が壊れる。
`--slurp` は「ページの配列」を返すので `.[][]` で二段階に平坦化する
（`--slurp` は `--jq` と併用できないため、`gh` の外でパイプして `jq` に渡す）。

万一マーカー付きコメントが複数見つかったら（並行セッションが同時に「無い」と判定して二重作成した等）、
**最小の id（最古）を正とし、残りは `gh api repos/{owner}/{repo}/issues/comments/<id> -X DELETE` で消す**。

### 作成と更新

本文は scratchpad に `status.md` として書き、`jq --rawfile` で JSON 化する。
Markdown 中のバッククォート・引用符・バックスラッシュを確実にエスケープするため、
`-F body=@file` の型推論は使わない:

```sh
jq -n --rawfile body "$STATUS_MD" '{body: $body}' > "$PAYLOAD"

# 新規作成（返る id を以降の更新で使う）
gh api repos/{owner}/{repo}/issues/<pr>/comments -X POST --input "$PAYLOAD" --jq .id

# 更新
gh api repos/{owner}/{repo}/issues/comments/<id> -X PATCH --input "$PAYLOAD" --jq .html_url
```

### 本文テンプレート

```markdown
<!-- pr-quality-loop-status -->
## 🔁 PR 品質担保ループ

**現在: Phase 1 — レビュー収集（1 周目）**

| Phase | 状態 | 内容 |
|---|---|---|
| 0 前提確認 | ✅ | base=`main` / 未コミット変更なし |
| 1 レビュー収集 | 🔄 1 周目 | CodeRabbit: 待機中(3/10 分) / codex: 完了(2 件) / claude: 実行中 |
| 2 統合・修正 | ⬜ | — |
| 3 動作証跡 | ⬜ | — |
| 4 最終報告 | ⬜ | — |

<sub>最終更新: 2026-07-31 08:12 JST</sub>
```

状態アイコン: `⬜` 未着手 / `🔄` 実行中 / `✅` 完了 / `⚠️` スキップ・要確認 / `❌` 失敗

### 更新タイミング

**各更新では、終えた Phase を `✅`（または `⚠️`）にすると同時に、次に入る Phase を `🔄` にし、
見出しの「現在: Phase N」も書き換える。** これを守らないと、Phase 1 のレビュー収集中や Phase 3 の
証跡取得中といった長い区間で、PR 側の表示が前のフェーズのまま古びる。

**3 レビュアーの個別状態は Phase 1 行の「内容」欄に併記し、レビュアーごとに行を分けない。**
行を分けると、片方が `⬜` のまま残って直列実行に見えてしまう（実際は並列で走っている）。

| # | タイミング | 書き込む内容 |
|---|---|---|
| 1 | Phase 0 完了直後 | コメントを作成（既存があれば再利用して初期化）。base と PR 番号。Phase 1 を 🔄 に |
| 2 | Phase 1 起動直後 | **3 レビュアーを並列起動したこと**を明示（CodeRabbit のポーリング上限も書く） |
| 3 | 各レビュアーの完了時 | Phase 1 行の内容欄をレビュアー単位で更新（先に終わった方から）。CodeRabbit を打ち切ったら ⚠️ と理由 |
| 4 | Phase 1 完了（3 レビュアーすべて完了 or 打ち切り） | レビュアーごとの指摘件数。**Phase 2 を 🔄 に** |
| 5 | Phase 2 の各周完了 | 周回数、レビュアーごとの対応 / 見送り。次周に入るなら **Phase 1 を 🔄 に戻す**、Phase 3 へ進むなら **Phase 3 を 🔄 に** |
| 6 | Phase 3 完了 | 証跡コメントへのリンク。**Phase 4 を 🔄 に** |
| 7 | Phase 4 完了 | 全行を確定し、残課題を併記 |

### 失敗時の扱い

- `gh` が失敗しても**ループ本体は止めない**（fork PR や権限不足でコメントできないことがある）
- 1 度失敗したらそのセッションではステータス更新を諦め、Phase 4 で「更新できなかった」と報告する
- Phase 3 の証跡コメントとは**別のコメント**にする（ステータスは可変、証跡は記録として残す）

## Phase 0: 前提確認

```sh
gh pr view --json number,title,url,baseRefName,headRefName
git branch --show-current
git status --short
```

- 未コミットの変更が残っていたら、ループを始める前にユーザーに確認する（レビュー対象が曖昧になるため）
- デフォルトブランチ（base）を控える。以降のレビューはすべて base との差分に対して行う

→ **ステータスコメントを作成する（#1）**

## Phase 1: レビュー収集（3 レビュアー並列）

**3 レビュアーは必ず同時に走らせる。** CodeRabbit のポーリング（最大 10 分）とローカル
レビュアーの実行（5〜10 分）は時間帯が重なるので、直列にすると待ち時間がそのまま加算される。

**この Phase ではファイルを一切変更しない。** レビュアーは全員 `git diff origin/<base>...HEAD`
を読むので、収集中に作業ツリーを触ると各レビュアーが別のコードを見ることになる。
CodeRabbit の指摘対応も Phase 2 まで持ち越す。

→ **ステータスコメントを更新する（#2）**

### 1-1. レビュー対象を固定し、ローカル 2 レビュアーをバックグラウンド起動

まず **3 レビュアー全員が同じコードを見る**よう、対象を固定する:

```sh
BASE=$(gh pr view --json baseRefName --jq .baseRefName)   # Phase 0 で控えたもの
REVIEW_SHA=$(git rev-parse HEAD)                          # 1-2 のポーリング基準にも使う
```

以降、レビュアーには必ず `origin/$BASE...$REVIEW_SHA` の差分を見せる。
起動が速いのでローカル 2 レビュアーを先に投げ、CodeRabbit の待ち時間に重ねる。

**codex**: `/codex-review` の手順に従う。特に以下を厳守:

- **Bash のバックグラウンド実行で起動する**（フォアグラウンドだとツールの制限時間で打ち切られ、
  そこまでの推論が丸損になる）
- タイムアウト付き（5〜8 分）で実行し、超過したら `pkill -9 -f codex` で掃除してタイムアウト扱いにする
- 実行後に `git branch --show-current` と HEAD を検証する。`codex review` が作業ブランチを別ブランチに checkout することがあるため、変わっていたら復元する

**別プロセス Claude Code**: 文脈を持たないフレッシュなレビュアーとして headless 実行する。codex と並行して Bash のバックグラウンド実行で走らせる（タイムアウト目安 10 分）:

```sh
claude -p "あなたは独立したコードレビュアーです。現在のブランチの origin/<base> との差分（git diff origin/<base>...HEAD）をレビューし、(1) バグ・ロジックエラー (2) セキュリティ (3) 設計・保守性 の観点で指摘を重要度順に列挙してください。各指摘には file:line、根拠、修正案を付けてください。差分に問題がなければ「指摘なし」と明言してください。" \
  --allowedTools "Read" "Grep" "Glob" "Bash(git diff:*)" "Bash(git log:*)" "Bash(git show:*)" "Bash(git branch:*)"
```

- `--allowedTools` を読み取り系に限定しているのは意図的（レビュアーに編集させない）

### 1-2. CodeRabbit のレビューをポーリング（1-1 の実行中に並行して行う）

push 直後は CodeRabbit のレビューがまだ投稿されていないことがある。

**必ず「レビュー対象のコミット」を基準に待つ。** 件数や存在だけを見ると、1 周目のレビューや
過去のレビューを検出して即座に終了してしまい、2 周目が実質スキップされる。

```sh
# レビュー対象の SHA を固定する（Phase 1 の冒頭で 1 回だけ）
REVIEW_SHA=$(git rev-parse HEAD)

# ポーリング: REVIEW_SHA に対する coderabbitai[bot] のレビューが現れるまで待つ
gh api "repos/{owner}/{repo}/pulls/{pr_number}/reviews" --paginate \
  --jq "[.[] | select(.user.login == \"coderabbitai[bot]\") | select(.commit_id == \"$REVIEW_SHA\")] | length"
```

- 返り値が 1 以上になったらそのレビューを対象として 1-2b へ進む
- 0 の間は 90 秒間隔で再確認する（上限 10 分）
- `commit_id` が使えない場合の代替: ポーリング開始前に既存レビューの id 集合を控えておき、
  それに含まれない新しい id が現れたら完了とみなす（`--jq '[.[] | select(.user.login == "coderabbitai[bot]") | .id]'`）

以下のいずれかに当たったら、その旨を記録して **CodeRabbit だけを打ち切る**（ローカル 2 レビュアーは止めない）:

- 上限まで待っても `REVIEW_SHA` に対するレビューが来ない
- このリポジトリに CodeRabbit が導入されていない
- **CodeRabbit のレート制限でレビューが生成されない**（複数 PR で続けて生成されない場合は待たずに打ち切る）

打ち切ったときは、ステータスコメントの内容欄に CodeRabbit の状態を `⚠️` と理由（レート制限 / 未導入 / タイムアウト）で残す。

**CodeRabbit が無くてもローカル 2 レビュアーは省略しない。** CodeRabbit が無い分、ローカル 2 レビュアーが唯一の
外部レビューになるため、2-1 の検証を飛ばさず指摘を 1 件ずつ確認する
（「指摘なし」だった場合も、それが結論であることを Phase 4 で明示する）。

### 1-2b. CodeRabbit の指摘本文を取得する（読み取りのみ）

Phase 2 で 3 者の指摘を統合するので、**この Phase で本文まで取り切る**（件数だけでは統合できない）。
`/coderabbit-fix` のうち**取得部分だけ**をここで行い、修正とスレッド返信は Phase 2 に回す。

```sh
# レビュー本文（サマリ）
gh api "repos/{owner}/{repo}/pulls/{pr_number}/reviews" --paginate \
  --jq '.[] | select(.user.login == "coderabbitai[bot]") | {id, commit_id, body}'

# インラインコメント（指摘の実体。path/line と本文）
gh api "repos/{owner}/{repo}/pulls/{pr_number}/comments" --paginate \
  --jq '.[] | select(.user.login == "coderabbitai[bot]") | {id, path, line, body}'
```

取得した指摘は scratchpad に保存し、Phase 2 で codex / claude の指摘と突き合わせる。
**対象リポジトリのファイルはここでは変更しない。**

### 1-3. 3 レビュアーの完了を待つ

- 先に終わったレビュアーの結果はステータスコメントの内容欄に随時反映する（#3）
- 全員が完了（または打ち切り）するまで Phase 2 に進まない。ポーリングだけが残った状態で
  待つのは構わないが、その間もファイルは変更しない

→ **ステータスコメントを更新する（#4）**

## Phase 2: 指摘の統合と対応（Phase 1 と合わせて最大 2 周）

### 2-1. 指摘の統合と検証

- CodeRabbit / codex / claude の指摘を統合し、同一箇所への重複指摘をまとめる
  （**複数のレビュアーが同じ箇所を指摘したものは優先度を上げる**。独立した目が一致した指摘は当たりやすい）
- **指摘を鵜呑みにしない**。1 件ずつコードを読んで妥当性を検証する（受け入れ基準は `/coderabbit-fix` の判断基準と同じ: バグ・セキュリティ・明白な規約違反は対応、意図的な実装への提案や過度な抽象化は理由を付けて見送り）
- 判断に迷う指摘はユーザーに確認する

### 2-2. 修正と push

- 妥当な指摘のみ修正する。指摘ごとにコミットを分ける
- **CodeRabbit の指摘は `/coderabbit-fix` の手順に従う**。ただし**インラインコメントの取得は
  1-2b で済んでいる**ので、ここでは「1 件ずつ対応/対応不要を判断 → 指摘ごとにコミット → スレッドに返信」だけを行う
- pre-commit フックが落ちたら修正して再コミットする（フックのスキップや `--no-verify` は禁止）
- **force push 禁止**。追加コミット + 通常 push で積む

### 2-3. 周回判定

- この周で「妥当と判断した新規指摘」が 0 件なら、2 周目を省略して Phase 3 へ
- 修正を push した場合は 2 周目へ（2 周目は修正後の差分に対して **Phase 1 から**やり直す。
  **`REVIEW_SHA` を push 後の HEAD で取り直す**こと。1 周目の SHA のままだと 1-2 のポーリングが
  1 周目のレビューを即座に検出して、CodeRabbit の再レビューを待たずに進んでしまう）
- 2 周で打ち切る。2 周目でも残った指摘は修正せず、Phase 3 で報告に回す

→ **各周の完了時にステータスコメントを更新する（#5）**

## Phase 3: 動作証跡の添付（マージ前ゲート）

**すべての PR** に、ローカルで動作確認した証跡を画像で貼る。これはマージ可否のゲートで、証跡が PR に「貼られている」状態になるまで "マージ準備完了" と報告しない。

証跡の形は PR の種類で変わる:

- **画面（UI）変更 PR** → dev サーバーを起動しブラウザで動作確認した画面スクショ
- **バックエンドのみの PR**（hub-api 等・UI なし） → `pnpm --filter <pkg> test` の pass 出力、または API レスポンス（curl 等）のスクショ

手順:

1. 上記の証跡を撮影する（Phase 2 の修正が固まった後に撮る。途中で撮ると古くなる）。保存先はセッションの scratchpad（file_upload が読めるのはセッション共有フォルダのみ）。
2. **claude-in-chrome 経由で user-attachments に自動添付する**（gh CLI では添付不可: `github.com/user-attachments/...` は web セッション cookie 経由のみ。ただし private リポジトリの user-attachments はリポジトリアクセス権者限定配信＝ org 内に閉じたままインライン描画・永続なので、これが本命経路）:
   1. `tabs_context_mcp` → `navigate` で PR ページを開く。GitHub 未ログインの 404 ならユーザーにログインを依頼（初回のみ。資格情報入力は自分では行わない）
   2. 新規コメント欄の file input `#fc-new_comment_field` は hidden なので、`javascript_tool` で可視化する: `el.hidden=false; el.style.cssText='display:block !important;...'; el.setAttribute('aria-label','evidence-file-upload-input')`
   3. `find` で ref を取得し `file_upload` で PNG を投入（コメントボタンは押さない）
   4. 3 秒ほど待って textarea（`#new_comment_field`）の value から挿入された `<img ... src="https://github.com/user-attachments/assets/<uuid>">` を取得
   5. **textarea を必ずクリア**（`ta.value=''` + input イベント dispatch）して下書き・誤投稿を残さない
   6. 取得した img タグを `gh api ... -X PATCH`（既存コメント追記）や `gh pr comment` で埋め込む
   - フォールバック（拡張がどうしても接続できない場合のみ）: ファイルを `~/Desktop` に置きキャプションを用意して、ドラッグ&ドロップだけユーザーに依頼する
3. 併せて、対象 issue の完了条件を 1 項目ずつ「どう確認したか」を対応づけて `gh pr comment` で PR にコメントする（証跡画像はこのコメントに埋め込むと 1 箇所にまとまる）。
4. 証跡が貼られる前に PR をマージ導線へ乗せない。並列 sub agent 運用では特に落ちやすいので、コーディネーターが PR ごとに添付済みかを確認する。

→ **ステータスコメントを更新する（#6）**。証跡コメントの URL を Phase 3 行に載せる

## Phase 4: 最終報告

以下をまとめてユーザーに報告する:

- 対応した指摘の一覧（コミットハッシュ付き）
- 見送った指摘と、その理由
- 2 周で解消しなかった残課題（あれば）
- push 後に CodeRabbit の新着コメントが増えていないかの最終確認結果
- **CodeRabbit をスキップした場合はその理由**（レート制限 / 未導入 / タイムアウト）と、
  代わりにローカル 2 レビュアーの指摘をどう確認したか
- **動作証跡がインライン添付済みであることの確認結果（コメント URL と画像描画確認）**
- **ステータスコメントの URL**（更新できなかった場合はその理由）

→ **ステータスコメントを最終状態に更新する（#7）**

## 原則

- レビューエージェントの指摘は検証してから直す。performative な同意（とりあえず全部直す）をしない
- コミットメッセージ・返信は日本語で書く
- 各フェーズの所要が長い場合も途中経過をユーザーに報告する
