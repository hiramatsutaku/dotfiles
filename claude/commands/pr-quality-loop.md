# PR 品質担保ループ

PR 作成後の品質担保を一括で行う。CodeRabbit 対応 → ローカル 2 レビュアー（codex + 別プロセス Claude Code）を最大 2 周 → 最終報告、の順で進める。

引数: PR 番号（省略時は現在のブランチに紐づく PR を `gh pr view` で特定する）。

## 全体フロー

```text
Phase 0: 前提確認
Phase 1: CodeRabbit レビュー待ち → 対応 → push
Phase 2: ローカル 2 レビュアー（codex + headless claude）→ 検証 → 修正 → push
         └ これを最大 2 周（新規の妥当な指摘が 0 なら 1 周で終了）
Phase 3: 最終報告
```

## Phase 0: 前提確認

```sh
gh pr view --json number,title,url,baseRefName,headRefName
git branch --show-current
git status --short
```

- 未コミットの変更が残っていたら、ループを始める前にユーザーに確認する（レビュー対象が曖昧になるため）
- デフォルトブランチ（base）を控える。以降のレビューはすべて base との差分に対して行う

## Phase 1: CodeRabbit 対応

### 1-1. レビュー完了を待つ

push 直後は CodeRabbit のレビューがまだ投稿されていないことがある。以下で coderabbitai[bot] のレビュー・コメントの有無を確認し、無ければ 90 秒間隔でポーリングする（上限 10 分）:

```sh
gh api repos/{owner}/{repo}/pulls/{pr_number}/reviews \
  --jq '[.[] | select(.user.login == "coderabbitai[bot]")] | length'
```

- 上限まで待ってもレビューが来ない、またはこのリポジトリに CodeRabbit が導入されていない場合は、その旨を記録して Phase 2 へ進む（ブロックしない）

### 1-2. 指摘対応

`/coderabbit-fix` の手順に従う（インラインコメント取得 → 1 件ずつ対応/対応不要を判断 → 指摘ごとにコミット → スレッドに返信 → push）。

## Phase 2: ローカル 2 レビュアー（最大 2 周）

各周で以下を行う。

### 2-1. 2 レビュアーを並列実行

**codex**: `/codex-review` の手順に従う。特に以下を厳守:

- タイムアウト付き（5〜8 分）で実行し、超過したら `pkill -9 -f codex` で掃除してタイムアウト扱いにする
- 実行後に `git branch --show-current` と HEAD を検証する。`codex review` が作業ブランチを別ブランチに checkout することがあるため、変わっていたら復元する

**別プロセス Claude Code**: 文脈を持たないフレッシュなレビュアーとして headless 実行する。codex と並行して Bash のバックグラウンド実行で走らせる（タイムアウト目安 10 分）:

```sh
claude -p "あなたは独立したコードレビュアーです。現在のブランチの origin/<base> との差分（git diff origin/<base>...HEAD）をレビューし、(1) バグ・ロジックエラー (2) セキュリティ (3) 設計・保守性 の観点で指摘を重要度順に列挙してください。各指摘には file:line、根拠、修正案を付けてください。差分に問題がなければ「指摘なし」と明言してください。" \
  --allowedTools "Read" "Grep" "Glob" "Bash(git diff:*)" "Bash(git log:*)" "Bash(git show:*)" "Bash(git branch:*)"
```

- `--allowedTools` を読み取り系に限定しているのは意図的（レビュアーに編集させない）
- レビュー中に自分（オーケストレーター側）が作業ツリーを変更しないこと。両レビュアーの完了を待ってから次へ進む

### 2-2. 指摘の統合と検証

- 両者の指摘を統合し、同一箇所への重複指摘をまとめる
- **指摘を鵜呑みにしない**。1 件ずつコードを読んで妥当性を検証する（受け入れ基準は `/coderabbit-fix` の判断基準と同じ: バグ・セキュリティ・明白な規約違反は対応、意図的な実装への提案や過度な抽象化は理由を付けて見送り）
- 判断に迷う指摘はユーザーに確認する

### 2-3. 修正と push

- 妥当な指摘のみ修正する。指摘ごとにコミットを分ける
- pre-commit フックが落ちたら修正して再コミットする（フックのスキップや `--no-verify` は禁止）
- **force push 禁止**。追加コミット + 通常 push で積む

### 2-4. 周回判定

- この周で「妥当と判断した新規指摘」が 0 件なら、2 周目を省略して Phase 3 へ
- 修正を push した場合は 2 周目へ（2 周目は修正後の差分に対して 2-1 からやり直す）
- 2 周で打ち切る。2 周目でも残った指摘は修正せず、Phase 3 で報告に回す

## Phase 3: 最終報告

以下をまとめてユーザーに報告する:

- 対応した指摘の一覧（コミットハッシュ付き）
- 見送った指摘と、その理由
- 2 周で解消しなかった残課題（あれば）
- push 後に CodeRabbit の新着コメントが増えていないかの最終確認結果

## 原則

- レビューエージェントの指摘は検証してから直す。performative な同意（とりあえず全部直す）をしない
- コミットメッセージ・返信は日本語で書く
- 各フェーズの所要が長い場合も途中経過をユーザーに報告する
